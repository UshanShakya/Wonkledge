# Architecture Context

## Stack

| Layer | Technology | Role |
| --- | --- | --- |
| Framework | Next.js 15 + TypeScript | Main full-stack web framework for the mobile-first app, dashboards, and API routes/server actions |
| UI | Tailwind CSS + shadcn/ui | Component styling, layout system, and accessible UI primitives |
| Auth | Clerk | Authentication, session management, user identity, and base role metadata |
| Database | PostgreSQL | Primary relational database for users, content structure, subscriptions, attempts, progress, payments, and review workflows |
| ORM | Prisma | Type-safe database schema, migrations, and data access |
| AI | OpenAI/Gemini provider adapter | AI feedback, grading, study recommendations, content draft generation, and explanations |
| Payments | eSewa, Khalti, IME Pay, Manual Verification | Subscription purchase and payment confirmation |
| File/Media Storage | Cloudflare R2, S3-compatible storage, or Supabase Storage | Images, uploads, receipts, CSV imports, PDFs, and admin source files |
| Video | Cloudflare Stream, Vimeo, YouTube unlisted/private, or external video provider | Video lesson delivery without building custom video infrastructure at MVP stage |
| Hosting | Vercel or equivalent for app; managed PostgreSQL for database | Deployment and infrastructure |
| Email/Notification | Resend, Clerk email, or provider abstraction | Emails for verification, payment status, feedback ready, study reminders, and admin notifications |
| Validation | Zod | Runtime validation for forms, API inputs, imports, and AI outputs |
| Analytics | Internal database events first | Track learning activity, revenue, content usage, AI usage, and admin analytics |

## Architectural Principle

Wonkledge must be built as a configurable learning platform, not as separate hardcoded apps for SEE/SLC, +2, Loksewa, or any other exam.

The same core data model must support all exam categories through configuration:

Exam Category → Track/Subject/Level → Chapter → Topic → Content → Practice → Feedback → Progress

New exams, levels, tracks, subjects, chapters, topics, and plans should be added from the admin panel whenever possible.

## System Boundaries

- `app/` — Next.js app routes, layouts, pages, and route groups.
- `app/(public)/` — Public pages such as landing page, pricing, about, and marketing content.
- `app/(auth)/` — Authentication entry pages if custom Clerk screens are used.
- `app/(student)/` — Student dashboard, learning pages, practice pages, mock tests, profile, subscriptions, and progress views.
- `app/(teacher)/` — Teacher/reviewer dashboard, review queues, grading screens, and feedback workflows.
- `app/(admin)/` — Admin dashboard, content management, subscriptions, payments, analytics, imports, AI generation, and review workflows.
- `app/api/` — Route handlers for webhooks, payment callbacks, file uploads, AI operations, imports, and system integrations.
- `components/` — Shared app components, domain components, layouts, and composed UI.
- `components/ui/` — shadcn/ui generated primitives. These are protected and should not be manually modified unless explicitly required.
- `features/` — Feature-specific modules such as learning, content, payments, subscriptions, AI, reviews, and analytics.
- `lib/` — Shared utilities, database client, auth helpers, validators, AI provider adapters, payment adapters, and access-control helpers.
- `server/` — Server-side business logic, data access functions, service functions, and workflow orchestration.
- `prisma/` — Prisma schema, migrations, and seed files.
- `types/` — Shared TypeScript types that are not generated by Prisma.
- `context/` — Product, architecture, UI, code, workflow, and progress documentation. These files are the source of truth for implementation decisions.
- `public/` — Static assets only.
- `scripts/` — One-off scripts for seeding, imports, maintenance, or data checks.

## Auth and Access Model

- Every user signs in through Clerk.
- Clerk stores identity and authentication state.
- The internal database stores app-specific profile, roles, subscriptions, progress, and permissions.
- A Clerk user must map to exactly one internal user record.
- A user may have one or more roles, but the app should prefer one primary dashboard role per session.
- Students access the student dashboard.
- Teachers/reviewers access the teacher dashboard.
- Admins access the admin dashboard.
- Super admins can access platform-wide admin controls.
- All server mutations must check authentication and authorization.
- Client-side hiding is not security. Server-side access checks are required.
- Content access must check free/premium status and all active subscriptions.
- A student can have multiple active subscriptions.
- Expiring one subscription must not remove access granted by another active subscription.
- Teacher review access must be controlled by role and review assignment/pickup rules.
- Admin content publishing requires the correct admin/reviewer permission.

## Content Access Model

Content can be:

- Free
- Premium but visible as locked
- Premium and hidden until subscribed
- Included in one or more subscription plans
- Included in bundles
- Draft
- In review
- Approved
- Published
- Rejected
- Archived

Students can only access content if:

1. The content is published.
2. The content is free, or the student has at least one active subscription that grants access.
3. The student's role and account status allow access.

Search may show locked premium content if admin settings allow previews, but it must not expose full paid content.

## AI Model

AI must be treated as an assistant, not the final authority.

AI can:

- Suggest study plans
- Analyze weakness/strength
- Generate explanations
- Grade subjective answers using rubrics
- Summarize mock test performance
- Generate content drafts for admins
- Suggest improvements

AI must not:

- Directly publish student-visible content without human approval
- Override admin/reviewer decisions
- Bypass subscription limits
- Run without usage logging
- Be used for unlimited free access

All AI requests must be logged with:

- User/admin ID when available
- Feature name
- Model/provider
- Input token estimate
- Output token estimate
- Estimated cost
- Request status
- Created timestamp

## Payment Model

Payment integrations must be isolated behind payment adapter functions.

Supported payment types:

- eSewa
- Khalti
- IME Pay
- Manual payment verification

Payment records must include:

- Student
- Plan
- Amount
- Currency
- Gateway
- Gateway reference
- Internal reference
- Status
- Payment date
- Verification status
- Linked subscription if successful

Never trust client-side payment success alone. Server-side verification or trusted gateway callback is required.

Manual payments must remain pending until admin approval.

## Invariants

1. Published student-visible content must never come directly from AI generation without human review and approval.
2. All premium content access must be enforced on the server, not only in the UI.
3. A student may hold multiple active subscriptions; access checks must consider all active subscriptions.
4. AI usage must be logged and cost-estimated for all AI-powered features.
5. Payment success must be verified server-side before activating a subscription.
6. Manual payment proof must not activate a subscription until approved by an authorized admin.
7. The system must remain exam-category agnostic; new categories should not require new code paths.
8. Content hierarchy must remain consistent: category/track/subject/level → chapter → topic → content.
9. Teacher-reviewed feedback must be approved or submitted by a teacher before it becomes final student feedback.
10. Draft, in-review, rejected, archived, or unpublished content must not be visible as normal study content to students.
11. Admin permissions must prevent content creators from approving their own content if the review workflow requires separation.
12. Do not store raw secrets, API keys, or gateway credentials in the database or source code.
13. Route handlers and server actions must validate input before mutation.
14. Long-running jobs such as bulk AI generation or large imports should be split into controlled background-safe units when infrastructure supports it.
15. The database is the source of truth for access, progress, payment, and content metadata.
